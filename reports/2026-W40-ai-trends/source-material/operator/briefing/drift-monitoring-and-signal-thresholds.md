# Drift monitoring and signal thresholds

## Editorial use

Use this file to explain monitoring as a decision system, not a dashboard decoration. The report should focus on what signals are watched, when a signal becomes actionable, and who decides whether to keep, limit, update, or pause an AI-mediated workflow.

## Source basis to cite cautiously

- NIST AI RMF supports ongoing measurement, monitoring, and risk management.
- FDA predetermined change control plan guidance supports bounded modifications, monitoring, validation, and response to performance deviations for AI-enabled device software functions.
- ONC/ASTP HTI-1 transparency materials support making source attributes and model information more visible in certified health IT contexts.
- CHAI assurance guidance supports lifecycle assurance, monitoring, evidence review, and accountability.

## Supported claims

- Drift monitoring should be linked to action thresholds, not simply stored as background analytics.
- Signals can include changes in patient mix, documentation practices, missing data, user overrides, alert burden, vendor updates, and outcome proxies where valid.
- Monitoring is more credible when an organization defines who reviews signals and what responses are available.

## Unsafe claims

- Do not claim drift monitoring proves fairness, safety, or clinical benefit.
- Do not claim a drift event occurred unless staged evidence says so.
- Do not treat all model updates as permissible or safe because a change plan exists.

## Evidence warning

The staged sources support monitoring and thresholds as governance mechanisms. They do not include measured drift, fairness, or safety results.
