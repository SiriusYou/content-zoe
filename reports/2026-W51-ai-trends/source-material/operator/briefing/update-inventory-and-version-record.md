# Update inventory and version record

## Editorial use

Use this file to make W51 about the record left by AI updates. The report should argue that a version number or vendor release note is not enough unless it connects the technical change to the local care workflow.

## Source basis

- FDA PCCP materials support bounded source context for planned changes to AI-enabled device software functions. Do not generalize them to all healthcare AI.
- ONC SAFER System Management supports safety practices around configuration, validation, maintenance, software, hardware, and interfaces.
- NIST AI RMF supports lifecycle documentation, context mapping, measurement, monitoring, and risk response.

## Reader-safe claims

- The update record should say what changed, when it changed, why it changed, who authorized it, and which local workflow uses it.
- The record should distinguish model updates, data-source updates, user-interface updates, integration updates, threshold or logic updates, prompt changes, permissions changes, monitoring changes, and support-process changes when the evidence allows.
- A local team should know whether the update affects the approved use, expected users, patient path, fallback route, escalation route, or evidence basis.
- Release notes should be translated into operational questions rather than filed as vendor paperwork.
- If the organization cannot tell what changed, that uncertainty should remain visible.

## Claims to avoid

- Do not claim a version record proves safe use.
- Do not claim all AI updates need the same approval process.
- Do not claim FDA PCCP recommendations apply outside their bounded device-software context.
- Do not invent release dates, version numbers, or update contents.

## Evidence limit

The staged sources support update-record questions. They do not include local version records, vendor release notes, change tickets, validation reports, or implementation proof.
