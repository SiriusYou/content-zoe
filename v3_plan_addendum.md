## 1. Re-instate `as_of` snapshot timestamp (HIGH — third time flagged)

**Add to `jobs` table:**

```sql
as_of TEXT NOT NULL  -- ISO8601 datetime locked at report:create
                     -- e.g. "2026-04-23T11:30:00Z"
                     -- Used to make re-runs of the same week deterministic
```

**`bin/report-create.ts`:** locks `as_of = new Date().toISOString()` at row insertion. Override-able via `--as-of <iso8601>` flag for back-dated reports.

**`pipeline/research.ts` prompt:** include the line:

> Use only sources published or dated up to **{as_of}**. Do not include items dated after this timestamp.

**Why:** without this, "week 2026-W17 AI trends" run on Apr 23 and re-run on May 3 produces different content because Codex's `--full-auto` web search returns whatever's current at runtime. No audit trail. Two prior reviews flagged this; both times it disappeared from the next revision. If it's intentional, document it explicitly.

## 2. Auto-git-commit failure stance (HIGH — new in v3)

**v3 plan introduced:** promote tx ends with `git add reports/<week>-ai-trends/ && git commit -m "[content-zoe] publish <week>"` after the SQLite tx commits.

**Locked stance: fail-loud, do not roll back the publish.**

**Add to `jobs` table:**

```sql
git_committed INTEGER NOT NULL DEFAULT 0  -- 0 = not committed; 1 = committed
git_commit_error TEXT                     -- captured stderr if commit failed
```

**`pipeline/promote.ts` post-tx logic:**

```
1. (Tx already committed: status=published, artifact_dir set, promoted event written.)
2. Run: git -C <repo-root> add reports/<week>-ai-trends/
3. Run: git -C <repo-root> commit -m "[content-zoe] publish <week>" --no-verify
        (--no-verify skips slow pre-commit hooks; auto-commit must remain fast)
4. On success: UPDATE jobs SET git_committed = 1.
   On failure: UPDATE jobs SET git_commit_error = <stderr>; emit
              events(type='git_commit_failed').
5. Bot reply to /approve includes git status:
   - success: "✓ published 2026-W17 (git: a1b2c3d)"
   - failure: "✓ published 2026-W17, but git commit failed: <stderr>. Run
              `cd content-zoe && git add reports/2026-W17-ai-trends/ && git commit -m '...'`"
```

**`bin/report-remind.ts` extension:** also lists `published AND git_committed = 0` jobs as "needs git commit."

**Preflight:** add to `bin/bot.ts` startup (alongside Codex version preflight):

```
- assert content-zoe is a git repo (git rev-parse --is-inside-work-tree)
- assert git config user.email is set; fatal if missing
```

These checks run once at boot, fail loudly. Catches the "I forgot to git init" case before the first /approve.

**Why:** the v3 plan added auto-commit silently (prior locked decision was "no auto-commit"). Without specifying failure handling, the system could end up in `status=published` + no git history with no surfaced error. The fail-loud + status-column pattern means the operator sees the issue at /approve time, not 3 weeks later when running `git log`.

## 3. Telegram notifier retry policy (MEDIUM — new in v3)

**v3 plan introduced:** `notified_at` + `last_notify_error` columns + a notifier loop. No retry policy specified.

**Locked policy: exponential backoff with cap.**

**Add to `jobs` table:**

```sql
notify_attempts INTEGER NOT NULL DEFAULT 0
notify_next_attempt_at INTEGER  -- unix ms; null until first failed attempt
```

**`telegram/notifier.ts` loop:**

```
1. SELECT jobs WHERE status='awaiting_approval'
   AND notified_at IS NULL
   AND (notify_next_attempt_at IS NULL OR notify_next_attempt_at <= now()).
2. For each: send Telegram message.
   On success: UPDATE jobs SET notified_at = now(), last_notify_error = NULL.
   On failure:
     - notify_attempts += 1
     - last_notify_error = <error>
     - notify_next_attempt_at = now() + backoff(notify_attempts)
   - Backoff schedule (notify_attempts → delay ms):
     1 → 30_000     (30s)
     2 → 60_000     (1m)
     3 → 120_000    (2m)
     4 → 300_000    (5m)
     5+ → 900_000   (15m, capped)
```

**`bin/report-remind.ts`:** lists awaiting_approval jobs with `notify_attempts >= 3` (3+ failed tries = something is genuinely wrong). Operator sees them and can investigate Telegram bot health.

**Why:** without bounded retry, a multi-hour Telegram outage means continuous polling + continuous failures, which can themselves trigger Telegram's per-bot rate limit. Exponential backoff is standard; 15m cap means you never wait more than 15m to see recovery.

## 4. Still-missing items from the prior addendum (MEDIUM — bake in during scaffolding)

These were in the v1 addendum's §D ("Remaining items"), absorbed into v3 partially, but two are still un-addressed:

| Item | Why it still matters |
|---|---|
| **`prompts/` directory with prompt templates as files** (`prompts/research.md`, `draft-en.md`, `edit-en.md`, `translate-zh.md`, `approval-summary.md`) | Plan now lists 5 stage handlers in `pipeline/`. Prompts as inline TS strings means they can't be diff'd cleanly across iterations and can't be opened by the operator for tuning without a TS editor. Stage handler does `Bun.file('prompts/research.md').text()` at startup. |
| **`runStage(stageDef)` helper** | With timeout + manifest-check + Evidence-Grade + prompt-injection wrappers + reject-history injection now per-stage, every handler is ~80 nearly-identical lines. Helper compresses to ~20 lines per stage + one ~60-line `runStage`. Without it, you'll have 5x duplication and 5 places to keep in sync when the pattern evolves. |

These are LOW severity individually but compound during implementation. Recommended: create the helper while writing the second stage handler, before duplication ossifies.

## 5. Open questions surfaced by this delta review

1. **`--as-of` flag interaction with `--force`:** if you `--force` re-create a job for a week that already has a published row, does the new attempt inherit the old `as_of` or get a new one? (Recommend: new one — re-running explicitly means re-snapshotting.)
2. **`git_committed = 0` rerun:** if `report:remind` shows a published-but-uncommitted job, is there a CLI to retry just the git commit step (`bun run report:retry-commit <job-id>`)? Or does the operator handle it manually? (Recommend: manual for v1; CLI for v1.1.)
3. **Notifier rate-limit on the *operator* side:** if 5 jobs all retry at the same backoff tick, the bot might send 5 Telegram messages in quick succession. Acceptable for personal use, but add a simple per-loop rate limit (max 1 send / 100ms) if the operator allowlist ever grows beyond one chat ID.
